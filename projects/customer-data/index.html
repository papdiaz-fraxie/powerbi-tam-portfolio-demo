Customer Data Reconciliation & Quality Pipeline

I designed a Python + BigQuery workflow to reconcile incoming client enrichment files against maintained reference data before manual research, while keeping human verification, QA reporting and repository reuse in the process.

What a recruiter should take from this project

A real customer-data workflow that combines reconciliation, data quality, human review and reusable reference data.

Problem

Client files of roughly 1,000–5,000 rows were previously researched record by record from scratch.

My role

Defined the matching rules, designed the workflow, tested outputs, debugged failures and iterated the process.

Technical approach

Python + BigQuery reconciliation using primary and fallback identifiers, freshness checks and QA controls.

Business value

Current matches could be verified in seconds; validated research fed back into BigQuery for future reuse.

Business problem

Every client file used to start from zero.

Clients supplied contact or account files for enrichment. Before the central repository and Python matching workflow existed, researchers worked through those files record by record, manually researching each row.

A researcher could normally build about 50 records per day from scratch, so repeated research consumed significant effort when the same contact or company might already exist in maintained data.

My response

Reconcile first, then verify or rebuild.

I designed and implemented a Python-based reconciliation workflow around the BigQuery repository. It checks incoming rows against the latest available reference data before research begins.

Every row still receives human review. The workflow accelerates known/current records without weakening the QA layer for stale, uncertain or unmatched records.

Operating model

A closed-loop enrichment workflow

Validated client research becomes reusable reference data instead of ending as a one-off spreadsheet.

1. Standardise intakeMap the client file into the controlled contact or account enrichment template.
2. ReconcileUse Python to match client rows against the maintained BigQuery repository.
3. Verify / researchResearchers review every row; current matches are quick to confirm while stale or unmatched rows need deeper research.
4. QA + deliverReturn the cleaned file with row-level outcomes plus a separate QA summary.
5. ReuseLoad the validated batch back into BigQuery through Python for future jobs.
Matching + freshness

Identity resolution was more than a name lookup

The public demo uses explicit match labels to make the logic easy to follow; production labels were less formal.

Contacts

Primary identifier: LinkedIn URL

  • Use LinkedIn URL as the strongest contact match where available.
  • If LinkedIn is missing, use supporting fields such as email, name and company.
  • Check recency and double-check that the person is still current.
  • Replace stale client values with the latest verified values when appropriate.
Accounts

Use multiple entity signals

  • Company LinkedIn URL
  • Website / domain
  • Company name
  • Country / location to disambiguate similar entities

Freshness matters: a database match was never treated as automatically current. Old or questionable matches were re-researched.

Data quality + client delivery

Controlled schema, visible exceptions, auditable outcomes

The standard enrichment templates included source, research date, status, batch and QA fields alongside the customer/contact attributes being enriched.

Controlled intake and provenance

  • Contact/account identity and company attributes
  • LinkedIn/profile, email, phone and location fields
  • Industry, employee-size, revenue and parent-company fields where relevant
  • Source and research date
  • Status, batch and QA notes

Examples of real QA outcomes

  • Duplicate
  • Valid contact but wrong title
  • Valid contact and correct title
  • Unable to find the account
  • Account Rebranded / Account Enriched
  • Invalid Company (Merged, Acquired, Sold)
Client deliverable: final cleaned/enriched file with row-level outcomes plus a separate QA summary/report. Unresolved or invalid records are visible rather than silently removed.

What I would improve next

Make confidence, lineage and monitoring more explicit

In a modern rebuild I would formalise the process with confidence scores, field-level lineage, schema tests, freshness monitoring and batch-level reconciliation metrics.

I would separate deterministic high-confidence rules from review-only candidate rules so match quality could be monitored over time without weakening human QA.
