Customer Data Onboarding, Reconciliation & Quality Pipeline

I designed a Python + BigQuery workflow that checks incoming client enrichment files against a maintained reference repository before research begins, then keeps human verification, QA reporting and repository reuse in the loop.

Business problem

Every client file used to start from zero.

Clients regularly supplied contact or account files for enrichment. Before the central repository and Python matching workflow existed, researchers worked through those files record by record, manually researching each row.

A researcher could normally build about 50 records per day from scratch. On a 1,000–5,000-record enrichment job, that makes repeated research expensive when some of the same contacts or companies may already exist in a maintained internal dataset.

My response

Reconcile first, then research what actually needs work.

I designed and implemented a Python-based reconciliation workflow around the existing BigQuery repository. The logic checks client records against the latest available reference data, surfaces likely matches, and gives researchers a stronger starting point before manual verification.

Every record is still reviewed by a person. The objective is not zero-touch automation; it is to avoid rebuilding known records from scratch while preserving a human QA layer.

Operating model

A closed-loop enrichment workflow

The completed client job does not end as a disposable spreadsheet. Newly verified records return to BigQuery through the same Python batch-loading process used for other validated data.

1. Standardise intakeMap the client file into the controlled contact or account enrichment template.
2. Python reconciliationMatch client rows against the maintained BigQuery reference repository.
3. Human verificationResearchers review every row; current matches are quick to confirm, while stale or uncertain rows need deeper research.
4. QA + deliveryProduce the cleaned/enriched file with row-level outcomes plus a separate QA summary for the client.
5. ReuseLoad the validated batch back into BigQuery through Python so future jobs can benefit from the refreshed data.
Important: repository matching does not remove row-by-row review. It changes the starting point: a current match can be verified in seconds, whereas a genuinely new or stale record still requires manual research.

Matching logic

Use stable identifiers first, then secondary evidence

The public demo makes the match categories explicit for clarity. The real production process was less formally labelled.

Contacts

LinkedIn URL is the primary identifier

  • Use LinkedIn URL as the strongest contact match where available.
  • If LinkedIn is missing, use secondary fields such as email, name and company.
  • Do not blindly trust a match: check recency and verify the person is still current.
  • Where the reference record is current, stale client values can be replaced with the latest verified values.
Accounts

Use multiple entity signals

  • Company LinkedIn URL
  • Website/domain
  • Company name
  • Country/location to distinguish similarly named entities

The production process used these signals in combination rather than relying on company name alone.

Freshness

A match was never treated as automatically current

The repository is continuously rebuilt and re-verified, which gives the team evidence about how quickly contact data becomes stale.

Behaviour-informed re-verification

Freshness thresholds were set conservatively based on observed change behaviour in the continuously maintained dataset rather than one universal expiry rule.

A current repository match could be checked in seconds, but researchers still double-checked it. If the record was old, questionable or inconsistent with current evidence, it moved into fresh research.

Why this matters

Contact data changes: people move jobs, titles change and company details evolve. Matching without recency controls would simply reproduce stale data faster.

The workflow therefore combines identity resolution + freshness + human validation, rather than treating matching as a single yes/no database join.

After

Repository-assisted verification

Python checks the client file against BigQuery first. When a current record is found, a researcher can verify that match in seconds rather than rebuild it from scratch.

Unmatched, stale or uncertain records still require the full research process, and every row remains subject to human review.

The benefit therefore scales with the number of usable current matches in a particular job. I deliberately do not invent a portfolio-wide savings percentage.

What this demonstrates

Customer-data engineering beyond a tool list

  • Standardised incoming customer/client files into a controlled schema.
  • Designed entity-matching logic using primary and fallback identifiers.
  • Integrated Python reconciliation with a BigQuery reference repository.
  • Built recency and human verification into the workflow instead of blindly trusting matches.
  • Used row-level QA outcomes and separate client QA reporting.
  • Closed the loop by loading validated enrichment batches back into BigQuery through Python for future reuse.
  • Tested, debugged and iterated AI-assisted Python code against a real operational process.
What I would improve next

Make confidence, lineage and monitoring more explicit

In a modern rebuild I would formalise the matching process further with confidence scores, field-level lineage, schema tests, freshness monitoring and automated reconciliation metrics by batch.

I would also separate deterministic high-confidence rules from review-only candidate rules so match quality could be monitored over time without weakening the existing human QA control.
