BigQuery Data Platform & Automation

I turned campaign-by-campaign B2B research stored in separate Google Sheets into a central, searchable BigQuery repository with layered QA, Python/SQL standardisation, historical record retention and automated data-request workflows.

Business problem

The research had value, but there was no repository.

Researchers manually built B2B contact and company data using LinkedIn, company websites and other online sources. Each client campaign or data project had its own Google Sheet.

Before the BigQuery repository existed, completed research stayed distributed across those campaign Sheets. When a similar requirement arrived later, there was no efficient central place to search what had already been built. A new list could take days or weeks to research from scratch depending on the brief.

My response

Turn one-off campaign research into a reusable data asset.

I created a BigQuery database to retain historical research and make it searchable for future client campaigns, CRM-related use, reporting, market analysis and Data-as-a-Service delivery.

The objective was not simply to move spreadsheets into a database. It was to preserve the research, improve consistency before ingestion and make the latest available build easy to reuse.

Operating model

How data moved from research to reuse

Quality control happened before BigQuery, not after a raw spreadsheet dump. Human QA and programmatic QA were separate layers.

1. Client briefCampaign or DaaS data requirement defines the target research.
2. Research SheetsResearchers build contacts and companies in separate Google Sheets using online sources.
3. Human QASpreadsheet formulas and human checking catch issues at the research stage.
4. Python / SQLI standardise fields and run additional checks before ingestion.
5. BigQueryHistorical builds are retained in the central repository; new extracts use the latest researched build.
Downstream access: the repository supports client campaign delivery, DaaS, CRM-related use, reporting and market analysis. I also built a Paperform → webhook → Apps Script → BigQuery workflow for form-driven data exports.

Why the scale matters

At roughly 208 client campaigns per year across the four complete years, repeatedly treating every campaign Sheet as an isolated dataset would waste accumulated research value.

The repository created a practical first question for a new data brief: what relevant, recent research already exists? Existing records could be reused and only the gaps needed new research.

Data quality

Layered QA before ingestion

The data was manually researched, so the main challenge was not only completeness. Different people and different campaign Sheets naturally introduced formatting and classification variation.

Layer 1 · Research QA

Formulas plus human review

  • Researchers entered data into campaign-specific Google Sheets.
  • Spreadsheet formulas were used to surface potential issues.
  • Human checking was completed before the data moved to my programmatic preparation stage.
Layer 2 · Python / SQL

Standardise and check again

  • Normalised country values such as Australia, AU and AUS.
  • Standardised inconsistent phone-number formats.
  • Standardised job-title and seniority values.
  • Checked required fields for blanks or missing values.
  • Checked duplicate records and other recurring data-quality issues.
  • Prepared validated data for BigQuery ingestion.

Historical data

Keep the history, use the latest build

A contact or company could be researched more than once across different campaigns. I retained historical builds in BigQuery rather than simply overwriting the old record.

Why this matters

People change jobs, titles, phone numbers and companies. The most useful record for a new campaign is normally the most recently researched build, but older research can still be valuable for history and auditability.

The downstream rule was therefore: retain historical research, but use the latest build when producing a new extract.

BigQuery-style latest-build pattern

WITH ranked AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY contact_key
      ORDER BY research_date DESC
    ) AS build_rank
  FROM `portfolio.contact_history`
)
SELECT * EXCEPT(build_rank)
FROM ranked
WHERE build_rank = 1;
Worked business example

How a new client list could be fulfilled

The repository changed the workflow from “start researching” to “check what we already know, then build the gap.”

1. Receive briefDefine market, company and contact criteria for the campaign or DaaS request.
2. Query repositorySearch BigQuery for historical records that match the requirement.
3. Apply recencySelect the latest researched build where multiple historical records exist.
4. Identify gapsReuse suitable existing research and send missing coverage back for new research.
5. DeliverFresh records pass QA and Python/SQL checks, then the combined data can be exported for the required downstream use.

Commercial value

Before the repository, a new list could take days or weeks to build from scratch because there was no central place to reuse prior work. The BigQuery repository turned historical research into a reusable asset: suitable records could be found quickly, the newest researched version could be selected, and research effort could focus on what was genuinely missing.

What this demonstrates

More than “I used BigQuery”.

  • Designed a central data repository around a real operational problem.
  • Combined human QA with programmatic data-quality controls.
  • Used Python and SQL to make manually researched data consistent and reusable.
  • Preserved historical builds while making recency part of downstream selection.
  • Connected BigQuery to form-driven operational workflows using Apps Script and webhooks.
  • Worked across data engineering, data quality, automation and commercial data delivery.
What I would improve next

Make the controls more observable and explicit.

In a modern rebuild I would formalise more of the existing operational logic into monitored data contracts: schema tests, source-level quality scores, scheduled validation reports, freshness alerts and clearer lineage from research build to downstream extract.

That would make quality and recency easier to monitor at scale while preserving the practical workflow that made the repository useful.
